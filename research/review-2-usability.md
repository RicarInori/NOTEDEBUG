## ② 需要具体化的模糊段落

### 2.1 §0 指标表 — "包体积"

> **原文**："核心 APK < 40MB，功能插件按需下发"

**问题**：未定义"按需下发"的机制。是应用商店的 Dynamic Feature Modules？自建 CDN 下载？首次启动后下载？离线场景如何处理？插件版本与主应用版本的兼容性校验？

**改进方向**：补充插件分发机制（至少一句话说明下载/安装/版本校验流程），或明确标注"v1.0 不做按需下发，全部内置"。

### 2.2 §0 指标表 — "崩溃率"

> **原文**："插件崩溃不影响主进程"

**问题**：这是架构特性，不是可量化的崩溃率指标。缺少真正的崩溃率目标（如 <0.1% session）和度量方式。

**改进方向**：改为"主进程崩溃率 < X%/session；插件崩溃率独立统计；度量方式：crash-free session rate"。

### 2.3 §2.2 核心不变量 — "inject 响应式"

> **原文**："storage provider 被替换（如本地存储 → WebDAV 同步存储）时，依赖方自动 Unloading → Loading → Active，无需重启应用"

**问题**：未定义替换的触发方式。用户在哪里操作？设置页面？插件市场？替换时正在进行的操作（如正在保存文件）如何处理？是否有过渡态 UI？数据迁移（本地→远端）是否自动触发？

**改进方向**：补充 provider 替换的用户交互流程、过渡态处理、数据迁移策略（至少引用到 §5 同步章节）。

### 2.4 §3.1 渲染管线 — "前置缓冲"

> **原文**："Android: GLFrontBufferedRenderer 语义 / iOS: CAMetalLayer presentsWithTransaction=false"

**问题**：GLFrontBufferedRenderer 是 Android 13+ API，低版本如何降级？`presentsWithTransaction=false` 在 iOS 上意味着放弃事务性提交（可能撕裂），是否接受？这些降级决策没有记录。

**改进方向**：补充降级策略表：Android 13 以下用什么？iOS 上是否接受撕裂？是否有 A/B 测试计划？

### 2.5 §3.3 笔刷系统

> **原文**："荧光笔用正片叠底混合防叠色，参考 Saber"

**问题**：仅一句话。正片叠底在 wgpu 中如何实现（blend state 配置）？是否需要 depth stencil 配合？多笔迹交叉区域的渲染顺序是否影响结果？

**改进方向**：给出 wgpu blend state 伪代码或引用调研 02 中的具体实现。

### 2.6 §4 PDF 底座 — "大文档性能"

> **原文**："目标指标对齐调研 03 §4.1：>100 页文档 58 FPS、内存 <100MB"

**问题**：58 FPS 是调研 03 中 SumatraPDF（基于 MuPDF）的数据，不是 PDFium 的实测数据。直接引用有误导风险。

**改进方向**：标注"目标值参考 MuPDF 引擎实测，PDFium 需 M3 阶段实测验证，若差距 >10% 需优化"。

### 2.7 §5.3 WebDAV 同步 — "冲突解决"

> **原文**："默认 LWW + 冲突副本（note (conflict 2026-10-12).nbk），三方合并留给远期 CRDT 插件"

**问题**：LWW 的时间精度（秒级？毫秒级？）未定义。时钟不同步场景（用户手动改系统时间）如何处理？冲突副本的 UI 展示方式？用户如何知道有冲突？

**改进方向**：补充 LWW 时间精度、时钟漂移容忍策略、冲突通知 UI 描述。

### 2.8 §8 里程碑路线图 — M1 验收标准

> **原文**："120Hz iPad Pro 实测延迟 <28ms"

**问题**：仅测 iPad Pro 不够。60Hz 设备（§0 指标 <40ms）的验收设备清单？低端 Android 平板的最低可接受延迟？测试工具/方法（高速摄像机？系统 trace？）

**改进方向**：补充测试设备矩阵和测量方法论。

### 2.9 §3.1 延迟预算 — 对象池

> **原文**："任何一环引入对象创建或锁竞争都是违规"

**问题**：方向正确但缺少具体指导。哪些对象需要池化？池的容量策略？Rust 中 `Vec`/`String` 的分配是否也算违规？（答案应该是栈分配/smallvec 可接受，堆分配需池化）

## ③ 术语/一致性问题

### 3.1 "插件"一词多义

文档中"插件"至少指代四种不同事物：

| 语境 | 含义 | 示例 |
|------|------|------|
| Cordis 插件 | cordis-rs 框架中的 Plugin trait 实现 | 任何 `apply(ctx)` 函数 |
| 功能插件 | 可安装/卸载的功能模块 | sync-webdav、shape-recognizer |
| 第一方预装插件 | 随应用分发但架构上是插件的模块 | ink-engine、pdfium-engine |
| 第三方 WASM 插件 | 沙箱隔离的外部扩展 | 社区开发的笔刷 |

**建议**：引入分层术语——"内部模块"(internal module) vs "可插拔功能"(feature plugin) vs "外部扩展"(third-party extension)，或至少在名词表中明确区分。

### 3.2 "Provider" vs "Service" vs "插件" 混用

- §2.3 用"Provider"指代 Service 的实现方
- §5.3 说"sync-webdav 是预装但可禁用的 Provider 插件"
- §6.2 说 stylus-generic 是"预装"，厂商插件"替换 generic provider"

**问题**：Provider 是 Cordis 概念还是本项目自定义概念？与 Service 的关系是什么？

**建议**：统一为 Definition → Provider → Consumer 三层，在名词表中定义。

### 3.3 延迟指标前后不完全一致

| 位置 | 指标 |
|------|------|
| §0 表格 | 120Hz < 28ms；60Hz < 40ms |
| §3.1 延迟预算 | "120Hz 目标 28ms"，预算分解合计 ~16ms（4+2+2+8），留 12ms 余量未说明 |
| §8 M1 验收 | "120Hz iPad Pro 实测延迟 <28ms" |
| 调研 02 §1.1 | "<40ms 即时响应"（通用阈值） |
| 调研 02 §8.2 | "120Hz < 28ms；60Hz < 40ms" |

**问题**：§3.1 预算分解 4+2+2+8=16ms 远小于 28ms 目标，12ms 余量是有意设计还是遗漏环节？60Hz 指标在 §3 中未复现。

**建议**：补充预算余量的用途说明（如"预留 shader 编译/jank 恢复"），60Hz 指标在 §3 中复现。

### 3.4 "Fiber" 与 "插件实例" 关系不清

§2.1 定义了 Fiber 是"插件生命周期的六态状态机"，但未明确：一个 Plugin 是否对应一个 Fiber？子插件是否有独立 Fiber？Fiber 与 Context 是 1:1 还是 1:N？

### 3.5 `.nbk` vs `.notebook`

- 主文档 §5.2 使用 `.nbk`
- 调研 03 §8 使用 `.notebook`

**建议**：统一为 `.nbk`（更短），在名词表中注明。

### 3.6 "笔迹" vs "笔画" vs "stroke"

文档中三个词混用：
- "笔迹渲染"（渲染管线整体）
- "一条笔画"（单个 stroke）
- `page_001.strk`（二进制笔迹文件）
- 调研 02 中 `stroke` 和 `ink` 也有区分

**建议**：定义——"笔画"(stroke) = 一次落笔到抬笔的连续点序列；"笔迹"(ink) = 页面上所有笔画的集合。

## ④ 建议的名词表条目

| 术语 | 定义 |
|------|------|
| **Context** | cordis-rs 的层级化服务容器，每个插件拥有一个子 Context，通过父链查找服务 |
| **Fiber** | 单个插件实例的生命周期状态机（六态），与 Context 1:1 绑定 |
| **Effect** | 经 Context 注册的、可逆的副作用操作，卸载时 LIFO 回收 |
| **Service / Definition / Provider / Consumer** | 三层接缝：Definition 定义 trait + 数据类型；Provider 是实现方（插件）；Consumer 是调用方 |
| **笔画 (stroke)** | 一次落笔→抬笔的连续 StylusData 点序列，是持久化和撤销的最小单元 |
| **笔迹 (ink)** | 一个页面或图层内所有笔画的集合 |
| **`.nbk`** | Inkweave 笔记文件的 ZIP 容器格式扩展名 |
| **预装插件 (built-in plugin)** | 随应用分发、默认启用、但架构上遵循插件协议的模块（如 ink-engine、storage） |
| **外部扩展 (extension)** | 第三方通过 WASM 沙箱加载的插件 |
| **前置缓冲 (front-buffered rendering)** | 允许渲染结果在 VSync 前部分进入显示管线，减少感知延迟 |
| **One Euro Filter** | 自适应低通滤波器，根据运动速度动态调整平滑强度 |
| **Triangle Strip** | 笔迹轮廓的三角带网格表示，支持单次 draw call 渲染 |
| **waterfall 事件** | Cordis 五模式事件之一，中间件链式分发，每环可改写或拦截 |
| **bail 事件** | Cordis 五模式事件之一，同步短路分发，首个返回非 null 值的监听器终止链 |
| **LWW** | Last Write Wins，基于时间戳的冲突解决策略 |
| **墓碑 (tombstone)** | 同步中标记已删除实体的记录，保留 N 天后物理清除 |
| **PlatformView** | Flutter 中嵌入原生视图的机制，本项目用于承载 wgpu 手写画布 |
| **StylusData** | 标准化手写笔输入数据结构（坐标/压力/倾斜/方位/时间） |
| **capabilities 位图** | 手写笔驱动声明的能力集合，UI 据此显隐功能入口 |

## ⑤ 文档结构改进建议

### 5.1 增加"快速开始"章节（建议作为 §0.5 或独立 §1）

当前文档从愿景直接跳到架构图。新人需要一条"从零到能写第一笔"的路径：

```
建议内容：
- 开发环境搭建（Rust toolchain + Flutter + 平台 SDK + PDFium 二进制）
- cargo build / flutter run 命令
- 第一个插件的编写（Hello World 级）
- 调试技巧（如何查看 cordis-rs fiber 状态、wgpu 调试工具）
```

### 5.2 增加 ADR（架构决策记录）索引

文档提到 ADR-001 但无索引。建议增加 `docs/adr/` 目录约定，并在文档末尾维护 ADR 列表。

### 5.3 §2 cordis-rs 应补充"不移植"清单

当前只说了移植什么（P0~P3），没说**不移植什么**。Cordis 的哪些特性被有意放弃？例如：
- Schema 校验（Config 校验是否移植？）
- Service 的 callable/可调用服务语义
- Context 的 `intercept` 机制
- `isolate` 服务隔离

### 5.4 §7 插件开发规范应补充完整示例

当前只有 `plugin.toml` 模板，缺一个完整的 WASM 插件代码示例（如激光笔插件的 Rust 源码骨架）。新人需要"照着抄就能跑"的模板。

### 5.5 增加"数据流图"章节

当前有架构图但没有数据流图。关键数据流需要可视化：
- 手写笔输入 → 渲染的完整数据流（含各层转换）
- 保存流程（UI 操作 → cordis event → storage plugin → 文件系统）
- 同步流程（本地变更 → sync plugin → WebDAV 服务器）

### 5.6 增加"已知技术债务"章节

v1.0 文档就应该记录已知妥协：
- Web 端降级策略的具体限制
- WASM 插件加载器 M6 才做，M0~M5 期间第三方插件如何开发？
